# Design: native Lua hooks for Dev CE (`debug.sethook` / `debug.gethook` that really fire)

Status: PLAN, nothing built. Written 2026-10-15 after the Frida debugger (`frida/live/cmds/luadbg.js`) proved the approach. Build 15038592 / 15296837 only (same HavokScript_FinalRelease.dll). Background: `findings/topics/lua-debugger-and-tuner.md`, handoff notes for the profiler: `findings/topics/lua-hook-engine-handoff-for-profiler.md`.

## Goal
Lua scripts (and WildW's CE `l_sethook`/`l_gethook` registration, unchanged) can call `debug.sethook(f, "lcr", count)` in any state that has the `debug` table and get call / return / line / count events, like PUC Lua 5.1. Also the base for a native debugger and profiler (same detour).

## Facts that decide the design
1. `lua_sethook` (exported) only stores fn / mask / count at `L+0xc8 / 0xd0 / 0xd4` and resets the counter `L+0xd8` and last-pc `L+0xe0`; `lua_newthread` copies them. The retail interpreter never reads them. So the VM side must be added: a detour in the loop.
2. Per-instruction fetch sites (all start `mov [L+0x30], pc`; pc not yet incremented): B `0x696aa`, A `0x620c0`, `0x646b0`, `0x65830`, `0x68346`. Displaced bytes at each site are two register/memory moves, no rip-relative, no branch (7,7,7,8,8 bytes). Which sites gameplay states use is UNKNOWN (UI states use B 0x696aa).
3. Reference semantics (Linux exe, DWARF-era build): `hks::debug_checkLineAndCountImpl(L, closure, pc)` (count at `+0xd8` vs `+0xd4`; line when the line of pc differs from the line of the last pc `+0xe0`, via the proto's line table) and `hks::debug_hook_call(L, event, pc, line)`: sets in-hook byte `L+0xdc`, `lua_getstack(L,0,ar)`, `ar->event` (offset 0, int) and `ar->currentline` (offset 0x28, int), guarantees 20 free API stack slots (`CallStack::growApiStack`, exported on Windows), calls `L+0xc8`, restores top, clears `L+0xdc`. Event ids: 0 call, 1 return, 2 line, 3 count (4 tail return).
4. The Windows `lua_State` layout differs from Linux in places (stack base `+0x50` here, `+0x60` on Linux). Windows-confirmed fields: callinfo base `+0x18` / top `+0x28` (24-byte entries), pc `+0x30`, stack top `+0x48`, stack base `+0x50`, in-hook byte `+0xdc` (the Release DLL clears `[L+0xdc]` after its debug call), hook block `+0xc8..+0xe0`. `lua_Debug` on Windows: `currentline` `+0x28`, `short_src` char[0x200] at `+0x40`, level at `+0x240`; `event` at `+0` is expected (getstack/getinfo never write it) and is verified by the self-test below.
5. THE REAL HAZARD: a hook may call Lua (PUC `hookf` calls the Lua hook function), which can reallocate the Lua stack. The interpreter keeps the frame base in a register plus spill slots, so after the hook the base must be reloaded. The SDK Release DLL's own debug branch shows the contract (variant A, rva 0x7d120): it calls out with `(debugger, L, closure?, pc)`, the callee returns the new base (`r13 = [L+0x50]`), and the loop stores it into both spill slots (`[rbp-0x80]`, `[rsp+0x78]`). Retail loops are the same source with that branch removed, so we recreate it per site: after the hook, reload base from `[L+0x50]` into the site's base register and its spill slot(s). Per site (from disassembly, to be re-verified by test): A (0x620c0/0x646b0): L=r13, pc=r15, base=r12, spill `[rsp+0x48]`; B (0x696aa): L=rdi, pc=rax, base=rcx, spill `[rbp+0x498]`; C (0x65830/0x68346): L=r15, pc=rdi, base=? (analyse; spill ?).
6. Dev CE already uses MinHook (function-entry hooks only, no register access), loads `HavokScript_FinalRelease.dll` with GetProcAddress, and registers Lua globals from `PushSharedGlobals` (`Main.cpp`). The GameCore proxy DLL is UNLOADED and reloaded when a game is loaded from the menu (this is what crashed the game earlier today when something pointed into the freed DLL). Any patch we leave in Havok must survive that.

## Design
### A. Detour stubs (not MinHook)
- One small stub per site, generated at runtime into executable memory allocated near HavokScript (`VirtualAlloc` within +-2 GB, then RX) so a 5-byte `jmp rel32` reaches it. Stub: save flags + volatile registers, align stack, `mov rcx,L ; mov rdx,pc`, `call [slot]` (indirect through a data slot in the stub block, see unload below), restore, if the call returned "stack may have moved" reload base register and spill slot(s) from `[L+0x50]`, execute the displaced original instructions, `jmp site+displaced_len`.
- Fast path in C++: `if (!(mask = *(int*)(L+0xd0))) return 0;` (plus a global "any hook active" flag). Estimated cost when no hook is set: a few ns per VM instruction (to be measured; see lazy patching).
- Build guard: byte-pattern check of all sites (and the `0x72f0` c_breakpoint cfunction) before patching; any mismatch -> log, features disabled, game untouched.
- Patch with other threads frozen (MinHook-style freeze: suspend all threads except ours around the 5-byte writes) because Lua runs on several threads.
### B. Lifetime / unload safety
- Stubs and their data slot live in the VirtualAlloc block, NOT in the DLL image. The slot holds the address of `OnFetch` in the Dev CE DLL. On DLL detach (and before GameCore reload) set the slot to a tiny no-op stub in the same block; on the next load detect "already patched" (magic in the block) and rebind the slot. Never leave a pointer into the freed DLL. (Alternative: restore the original bytes on detach with threads frozen; costs more, same effect.)
### C. Lazy patching
- Do not patch at DLL load. Patch on the first `debug.sethook` with a non-zero mask (and keep it). Runs without hooks keep the original VM speed.
### D. Honouring the mask
- count (8): `++*(int*)(L+0xd8) >= *(int*)(L+0xd4)` -> event 3, reset counter.
- line (4): fire when the pc is the first instruction of a line or a backward jump (`pc <= last pc`). Phase 1: classification through exported `lua_getstack/lua_getinfo` ("Sl", writing `L+0x30` first, as luadbg.js does) cached per pc in a lock-free table; Phase 2: decode the proto line table natively (offsets from the Windows getinfo path, 0x3cc10) and drop the cache (its weakness: stale entries when the GC frees code).
- call (1): at a fetch where callinfo depth is larger than for the previous fetch of this `L` (first instruction of a new Lua function = PUC call-hook point). C-function calls: later phase (needs the call handlers; Linux has `Debugger::OnCFunctionCall`).
- return (2): needs the OP_RETURN / OP_TAILCALL handlers (opcode = index in the jump tables A1 `0x655d0`, A2 `0x69464`, B `0x6d7f4`, 92 entries each). Find them by tracing which handlers run for tiny known chunks; detour each with a stub that fires the event before the frame is popped. Phase 2.
- `OnFetch` runs the Linux-style hook call: skip if `L+0xdc` is set; set it; `L+0x30 = pc`; `growApiStack(L, 20)`; `getstack(L,0,ar)`; fill `event` and `currentline`; call `L+0xc8`; restore `L+0x48`; clear `L+0xdc`; return "base may have changed" = true.
### E. Lua API
- Implement `debug.sethook([thread,] f, mask [, count])` / `debug.gethook([thread])` in C++ ourselves (a PUC `db_sethook`/`hookf` port: the Lua function lives in a registry table keyed by thread; `hookf` pushes the event name `"call" "return" "line" "count" "tail return"` and the line, then `lua_call`s it), registered next to the other debug functions. Rationale: WildW's `l_sethook` is an internal non-exported symbol of the PUC library and was only ever a thin `lua_sethook` wrapper; if his registration is kept it works unchanged once the VM fires hooks, provided its `hookf` reads `event` at 0 and `currentline` at 0x28.
- Also make `debug.c_breakpoint(name)` pause (the Frida prototype already does; native version = same replacement of the `0x72f0` cfunction) only when a native debugger/profiler front end asked for it, else a no-op.
### F. Where it lives
- New files `LuaHooks.cpp/.h` (stub generator, OnFetch, Lua API), small and self-contained so WildW's CE can take the same file. Branch `feature/lua-hooks` off `dev` in `publish/civ6-dev-ce` (per the agreed git workflow), docs in `civ6-gamecore-reference`.

## How we verify
1. Startup self-checks (log in DevBridge.log): site byte patterns, `L+0xdc` is 0 on a fresh state, `getstack` level-0 line equals the expected line for a probe chunk.
2. Lua self-test in the DevCE_Test mod (runs in the Main State / any state with `debug`): (a) line hook on a 5-line function must produce exactly the expected line sequence and agree with `debug.getinfo(1,"l").currentline`; (b) count hook with count=100 on a loop of known size fires the expected number of times; (c) call/return on nested functions (phase 2); (d) a hook that calls a deeply recursive Lua function (forces stack reallocation) must not crash and the hooked code must still compute the right result (tests the base reload); (e) an error inside a hook is caught by pcall; (f) hooks are inherited by new coroutines and `sethook(co, ...)` works per thread; (g) turning the hook off restores normal behaviour.
3. Oracle: the Frida `luadbg.js` breakpoints on the same lines must stop where the native line hook fires.
4. Safety/performance: Lua micro-benchmark before first sethook, after patch with mask 0, and with a line hook; a full end-turn with hooks off after patching; load a game from the menu twice (unload safety).
5. First tries on a disposable single-player save, UI state first, gameplay states after counting which sites they use.

## M0 RESULTS (2026-10-15, Frida probes `frida/live/cmds/m0.js`, in game, ~30M fetch hits)  VERIFIED unless noted
1. Site usage: ONLY site B (0x696aa) ever ran: UI states and gameplay/worker states, 8+ threads, 16+ lua_States, idle and during an end-turn (4.1M hits in one turn). Sites A (0x620c0, 0x646b0) and C (0x65830, 0x68346) had ZERO hits in this mod set. Plan: patch B only; A/C optional and unverified (guard them: if their counters ever move, refuse hooks there).
2. Register contract for B: at the hook point `rdi`=L, `rax`=pc, `rcx`=frame base, spill slot `[rbp+0x498]`; base == spill == `[L+0x50]` on every hit (0 violations in ~30M hits, all threads/states).
3. Stack reallocation: forced real Lua stack moves (luaL_checkstack growth, `[L+0x50]` changed, e.g. 0x1dcd2daf0 -> 0x81b88060) at a fetch site of four different states (one game-thread UI state, one with 8 threads, one worker-only state) and applied the contract (reload rcx and `[rbp+0x498]` from `[L+0x50]`): the game kept running normally (ticks, no Lua errors in Lua.log). Sufficiency shown; necessity not shown (no negative control, it would crash the game).
4. Opcodes (instruction word >> 25) by next-instruction call-depth change over 6 traces: 69 and 2 always raise the depth (calls of Lua functions), 3 raises it for Lua callees and keeps it for C callees (generic call), 9 lowers it (RETURN). So call/return events need no extra handler hooks: in the fetch hook read `op = *pc >> 25`; fire CALL when depth grew since the previous fetch of this state (first instruction of the new function) and RETURN before executing op 9. Tail calls/other return forms not examined.
5. Frame top: `L->top` (`+0x48`) is the frame top: `(top-base)/16` is the function's frame size (seen 2, 4, 10, 25, 36 slots) and the destination register A (low byte of the instruction) was below it in 342,000 of 342,000 fetches, so a hook may push above `top`. (Callinfo entry layout: `[0]` frame base, `[1]` caller's saved pc, `[2]` flags/count word; 24 bytes each; `L+0x28` points at the CURRENT entry.)
6. Still open: lua_Debug `event` offset (Linux code writes it at +0; Windows to be proven by the in-game self-test); native line-table layout (phase 2); thread safety of getstack/getinfo (M2). RESOLVED: chunks run via loadstring+pcall (Frida `lua`, tuner `CMD:`) DO pass site B; the earlier "no hits" were an artifact (a 3M-iteration loop under five stacked Frida listeners ran at ~4 us per instruction, so the counters barely moved when read; the loop later finished and the game recovered by itself, with the counters then at 11.5M hits and still 0 contract violations and 0 of 11.5M fetches with register A >= frame top).
7. INCIDENT / lesson for probe work: after several re-installs of probe CModules (each `Interceptor.attach` is permanent, so 4-5 stacked listeners ended up on every hot site) plus a 3M-iteration chunk run on the game thread, the game thread got stuck in Frida's interceptor bookkeeping (a loop over the per-thread invocation stack, 0x9e0-byte entries) with the process growing to ~9-10 GB and ticks frozen for several minutes; the game eventually recovered by itself (memory stayed high, restart before further tests). Rules: install a probe ONCE per game session (change the cmds file only in ways that reuse the installed CModule), never run long loops under hooks, keep hot-site listeners to one.


## M1 RESULTS (2026-10-15)  VERIFIED in game: LuaHooks.cpp (branch feature/lua-hooks), self-test DevCE_HookTest.lua 18/18 PASS
- Built as designed: generated stub at the single fetch site B (0x696aa), lazy install on the first debug.sethook with a non-zero mask (logged in DevBridge.log), own `debug.sethook` / `debug.gethook` (current thread only; no thread argument), `DevCE_ClockMs()` high-resolution clock. The DLL is pinned (DllMain), so the stub calls straight into it; the stub block lives in VirtualAlloc memory near the Havok module and survives save reloads (patch logged once per process).
- Checks that pass: gethook states; line events on the real source lines ([58,42,43,44,45,59]); `getinfo(2).currentline` equals the line argument inside a hook (needs L+0x38 = hook pc and L+0x40 = hooked frame index around the hook call, as Linux hks::debug_hook_call does; the pc lookup is HavokScript+0x28180); one line event per iteration of a single-line loop (backward jump rule); count hook (~1 per 100 instructions); call/return in order; a hook that recurses 500 deep (moves the Lua stack) while the hooked code keeps computing correctly; an erroring hook is logged and removed (divergence from PUC, which would propagate the error); coroutines created under a hook mask; results of hooked loops unchanged.
- Cost (3M-iteration loop, ms): before the patch 27.8, patch installed with no hook 28.5 (about 2 %, noise level), count hook every 1000 instructions 135 (the slow path costs roughly 12 ns per VM instruction), 100k iterations with a line hook calling a Lua function 100,008 events in 29.6 ms (about 0.3 us per event).
- Learned along the way: proto layout (from the getinfo 'l' code at 0x3cf20): code start `[proto+0x20]`, debug info `[proto+0x48]`, line array `[debuginfo+0x10]` indexed by `(pc - code start) / 4`; the frame-pc lookup 0x28180 returns `[L+0x38]` when the frame index equals `[L+0x40]`, else the saved pc in the callinfo entry above it.
- Still open / next: hooks for C function calls/returns and tail returns; `debug.sethook(thread, ...)`; native line lookup using the proto layout (drops the getstack/getinfo cache); breakpoints and a socket debugger on top (replaces the Frida prototype); run the self-test in more contexts (UI state, other builds), a full end-turn with a hook active in gameplay Lua; PR to WildW's CE.
